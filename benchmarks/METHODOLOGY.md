# Benchmark methodology

Every "before" number in this repo comes from branch `baseline-v1-bench`, which is the tag
`baseline-v1` (74c6446) plus the four behaviour-neutral hooks below and the `benchmarks/` folder.
No other app code differs. Verify with:

```bash
git diff baseline-v1 -- backend/
```

## App-code changes (complete list)

All hooks default to the exact previous behaviour when the env var is unset.
Caveat: an env var set to an empty string is *not* treated as unset (`??`, not `||`).

| File | Before | After |
|---|---|---|
| `backend/src/server.ts` | `startCronJobs();` | `if (process.env.DISABLE_CRON !== "true") startCronJobs();` |
| `backend/src/services/leetcode.service.ts` | `const LEETCODE_GRAPHQL_URL = "https://leetcode.com/graphql";` | ``const LEETCODE_GRAPHQL_URL = `${process.env.LEETCODE_BASE_URL ?? "https://leetcode.com"}/graphql`;`` |
| `backend/src/services/codeforces.service.ts` | `` `https://codeforces.com/api/user.info?handles=${handle}` `` | `` `${process.env.CODEFORCES_BASE_URL ?? "https://codeforces.com"}/api/user.info?handles=${handle}` `` |
| `backend/src/services/codechef.service.ts` | `` `https://www.codechef.com/users/${username}` `` | `` `${process.env.CODECHEF_BASE_URL ?? "https://www.codechef.com"}/users/${username}` `` |

Deliberately *not* changed (they are part of the baseline): no HTTP timeouts, `console.*` logging,
sequential `runAllSnapshots`, the in-memory cache, etc.

## Rules

- Baseline numbers come only from `baseline-v1-bench`. Before/after comparisons use the same machine,
  dataset (seed, anchor date, scale), mock-platform settings and load profile.
- Never hit the real LeetCode/Codeforces/CodeChef. Always set the three `*_BASE_URL` vars to the mock.
- Run the API with `DISABLE_CRON=true`, `NODE_ENV=production`, against the bench DB on :5433.
- Raw outputs go under `benchmarks/results/`. Anything not yet measured is `[MEASURE]` in docs.
- If a result looks too good, check cache hits, error responses and rate limiting first.

## Dataset (seeder)

`seed/seed.ts`, deterministic (`--seed`, default 1; `--anchor` pins "today"; same flags give identical
checksums, verified by seeding twice). The mock server and seeder share `lib/gen.mjs`, so seeded
`rawData` has exactly the shapes the app would store.

- Platforms: ~80% LeetCode, ~50% Codeforces, ~30% CodeChef (independent draws; ~7% of users have none).
  Observed at 1k users: 800 / 503 / 282 accounts.
- ~10% `GROUPS_ONLY`. Branches from `VALID_BRANCHES`, skewed (CSE 30%, IT 18%, ... CHE 6%); batch years 2021-2027.
- History: `--days` (180) x `--snapshots-per-day` (4) PlatformSnapshots per account.
  `DailyActivity` exists for LeetCode accounts only (as in the app), generated by a bounded random walk
  of per-day activity probability over 365 days, zero days omitted. `currentStreak`, `totalActiveDays`
  and `lastActivityDate` are derived with the same rule as `processAccountSnapshot`.
- Groups: one of 50, one of 500 (capped at N), and N/15 small groups of 3-30. Membership is sampled uniformly.
- `rawData` sizes (1k run, JSON text): LeetCode ~2.6 KB (about 170 active days in the calendar, stored ~1.4 KB
  after TOAST compression), Codeforces ~0.4 KB, CodeChef ~60 B. Real heavy LeetCode users can exceed this;
  M12 storage numbers describe *this* dataset, not production.
- Constraints and indexes stay in place during load (fidelity over load speed). After load:
  `rebuildLeaderboard()` (from the built backend) then `VACUUM (ANALYZE)` on every table, then
  `pg_stat_statements_reset()` so measurements start clean.

### Scale tiers

## Environment (fill in per run in results)

Recorded for the harness validation run (not a benchmark result):

- Machine: Apple M4, 16 GB RAM, macOS (Darwin 27.0.0); Node v22.22.3
- Docker via Colima VM (4 vCPU / 6 GB); Postgres container capped at `cpus: 2`, `mem_limit: 2g`
- Image `postgres:16` (16.15), digest `sha256:f9a7b9eb...b029657`; `shared_buffers=512MB`, `work_mem=16MB`,
  `effective_cache_size=1GB`, `pg_stat_statements.track=all`
- API and k6 run on the host, outside the DB container's limits (they compete with the VM for host CPU: note this in results).
